# Project API Contract — v0.1

Статус: черновик на совместное ревью (PR #32, без изменения серверного кода)
Автор: Виктор (Obedkov-Viktor) · Обновлено: 2026-11-20 (правки по ревью P2.2a)
Основание: архитектура Project → Work → Document → Revision, CAS, receipts,
проверка владельца и курсорная пагинация из `server/projects/`

## 1. Назначение

Контракт Project API фиксируется **до реализации**, чтобы frontend (Workspace/Canvas)
и backend развивались параллельно без конфликтов архитектуры. Реализация опирается
на существующие механизмы; параллельное хранилище не создаётся.

В этом PR — только документация. Серверный код не изменяется, тестовые
ограничения (`NOT_GRANTED` и др.) не снимаются.

Версия контракта: **API 0.1**. Значение возвращается в поле `apiVersion`
каждого ответа; ломающие изменения контракта повышают версию.

## 2. Общие соглашения

1. **Транспорт:** HTTPS, JSON only (`application/json; charset=utf-8`).
2. **Аутентификация:** только серверная сессионная cookie `wdeaf_session`.
   Клиент не передаёт идентификатор аккаунта ни в query, ни в теле.
   Владелец определяется исключительно из серверной сессии.
3. **Ошибки:** единый формат с машиночитаемым кодом:

   ```json
   {"error": {"code": "INVALID_CURSOR", "message": "Некорректный курсор."}}
   ```

   Внутренние детали (стек, пути, SQL) клиенту не раскрываются.
4. **Origin:** не-GET/HEAD запросы с чужим `Origin` отклоняются (403) —
   поведение уже реализовано в `server/index.mjs`.
5. **Даты:** ISO 8601, UTC, миллисекунды (`2026-11-19T10:00:00.000Z`).
6. **Идентификаторы:** выдаются только сервером, для клиента — непрозрачные строки.
7. Неизвестные и повторные query-параметры — `400 INVALID_QUERY`.
8. **Кэширование:** все ответы методов `/api/*` отдаются с заголовком
   `Cache-Control: no-store` (данные персональные и быстро меняются;
   поведение уже реализовано в `server/index.mjs`).

## 3. Методы v0.1

В v0.1 реализуется один метод — список проектов. Методы создания, чтения
и сохранения документа описаны в п. 5 как предварительное направление
(их контракты — отдельными PR после утверждения этого документа).

### GET /api/projects

Возвращает страницу списка проектов **только текущего владельца**.

#### Запрос

```
GET /api/projects?limit=20&cursor=v1.<...>
Cookie: wdeaf_session=<...>
```

| Параметр | Тип | Обязательность | Описание |
|---|---|---|---|
| `limit` | int | нет | Размер страницы. По умолчанию **20**, допустимый диапазон **1–50**. Значение вне диапазона или не число → `400 INVALID_LIMIT`. |
| `cursor` | string | нет | Непрозрачный курсор из `nextCursor` предыдущего ответа. Клиент не конструирует и не разбирает курсор. Некорректный, чужой или инвалидированный курсор → `400 INVALID_CURSOR`. |

#### Ответ `200 OK`

```json
{
  "apiVersion": "0.1",
  "items": [
    {
      "id": "prj_...",
      "type": "web-application",
      "status": "active",
      "name": "Лендинг кафе",
      "createdAt": "2026-11-19T10:00:00.000Z",
      "updatedAt": "2026-11-19T12:30:00.000Z"
    }
  ],
  "nextCursor": null
}
```

Элемент `items[]` — **ProjectSummary**, согласованный с моделью P2.2a:

| Поле | Тип | Описание |
|---|---|---|
| `apiVersion` | string | Версия контракта (`"0.1"`). Позволяет frontend явно проверять совместимость. |
| `items[]` | array | Проекты владельца, сортировка по `updatedAt` по убыванию. Пустой список — валидный ответ (см. п. 4). |
| `id` | string | Серверный идентификатор проекта (Project). |
| `type` | string | Тип проекта. Согласовано с P2.2a: в v0.1 единственное значение — `"web-application"`. Новые типы добавляются расширением контракта. |
| `status` | string | Жизненный статус. Согласовано с P2.2a: в v0.1 — `"active"`. Другие значения (архивирование и т.п.) вводятся отдельным расширением контракта; удалённые (soft-deleted) проекты в список не включаются. |
| `name` | string | Отображаемое название проекта (см. открытый вопрос п. 7). |
| `createdAt` / `updatedAt` | string | Даты создания и последнего изменения (ISO 8601 UTC). |
| `nextCursor` | string \| null | `null` — страница последняя. Иначе передаётся в `cursor` следующего запроса. |

Поле `headRevisionId` в ProjectSummary **не включается в v0.1**: необходимость
его присутствия в списке решается отдельно (см. открытый вопрос п. 7).

#### Поведение в особых случаях (фиксируется явно)

| Ситуация | Ответ |
|---|---|
| Сессия отсутствует, истекла или отозвана | `401 UNAUTHORIZED` |
| У пользователя нет своих проектов | `200 OK` с `"items": []`, `"nextCursor": null` |
| Чужой, битый, просроченный или инвалидированный курсор | `400 INVALID_CURSOR` |
| Проекты других аккаунтов в выдаче | Невозможны по построению (п. 4 реализационных требований) |

#### Ошибки

| Код HTTP | `error.code` | Когда |
|---|---|---|
| `400` | `INVALID_QUERY` | Неизвестный или повторный параметр |
| `400` | `INVALID_LIMIT` | Недопустимое значение `limit` |
| `400` | `INVALID_CURSOR` | Курсор битый, чужой, просрочен или инвалидирован |
| `401` | `UNAUTHORIZED` | Сессия отсутствует, истекла или отозвана |
| `429` | `RATE_LIMITED` | Превышен лимит запросов (+ заголовок `Retry-After`) |
| `500` | `INTERNAL` | Внутренняя ошибка |
| `503` | `STORAGE_UNAVAILABLE` | Хранилище временно недоступно (например, сбой/блокировка SQLite). Клиент может повторить запрос с паузой |

`404` у этого метода нет: список без прав — пустой список, а не ошибка.

## 4. Проверка владельца

1. Аккаунт определяется исключительно из серверной сессии (durable store).
2. Фильтрация по владельцу — на уровне SQL (`account` в схеме хранилища),
   переиспользуя существующие механизмы `server/projects/`.
3. Горизонтальный доступ неразличим: чужой курсор или подменённые данные
   дают тот же ответ, что и отсутствие данных (`400 INVALID_CURSOR` /
   пустой `items`), без разглашения существования чужих проектов.
4. **Обязательное тестовое требование:** сценарий двух разных аккаунтов —
   пользователь B не получает данные пользователя A ни в `items`,
   ни через подмену курсора, ни при повторном использовании чужого курсора.

## 5. Предварительное направление следующих контрактов (вне scope v0.1)

Маршруты ниже — **предварительные**. Их сигнатуры, коды ошибок и связи
с моделью **Project → Work → Document → Revision** согласуются отдельными PR
в этом же документе, с опорой на CAS и receipts:

- `POST /api/projects` — создание проекта (idempotency key → receipt).
- `GET /api/projects/{id}` — чтение проекта и документа по ревизии.
- `PUT /api/projects/{id}/document` — сохранение документа с optimistic
  concurrency (`expectedRevisionId`), CAS-хранение содержимого, receipt
  на каждую операцию записи.

Пункты зафиксированы, чтобы frontend видел траекторию API; до отдельного
согласования они не являются обязательством контракта.

## 6. Пагинация и правила инвалидирования курсора

1. Модель — курсорная (offset не используем: список меняется во время
   пролистывания).
2. Курсор непрозрачный, подписанный HMAC (алгоритм — деталь реализации),
   с ограниченным временем жизни.
3. Курсор инвалидируется, и сервер отвечает `400 INVALID_CURSOR`, когда:
   - истекло время жизни курсора;
   - нарушена подпись (битый или сфабрикованный курсор);
   - курсор выдан другому аккаунту;
   - список проектов владельца наблюдаемо изменился (создание, удаление,
     изменение порядка) с момента выдачи курсора.
4. Получив `400 INVALID_CURSOR`, клиент начинает пролистывание с первой
   страницы (без параметра `cursor`). Хранить курсор дольше одной сессии
   пролистывания клиент не должен.

## 7. Открытые вопросы (до утверждения контракта)

1. **`name`:** есть ли название у проекта в текущей модели Workspace frontend?
   Если нет — обязательное поле при создании или сервер генерирует
   («Проект от <дата>») до появления редактирования?
2. **`headRevisionId` в списке:** нужен ли он frontend в ProjectSummary
   (как точка входа для чтения документа), или достаточно получать его
   при чтении проекта по `id`? Решение — отдельно, до реализации.

## 8. Статус хранилища и границы этого контракта

1. Существующий тестовый контур хранилища (G1b / `server/projects/`,
   `DisposableMetadataStore`, `TestFixtureAuthority`, `NOT_GRANTED`)
   **не является production-ready** и этим документом в эксплуатацию
   не переводится.
2. Подключение постоянного хранилища (файл SQLite в `DATA_DIR`) и снятие
   ограничений (`NOT_GRANTED` и др.) требуют **отдельной проверки
   и явного разрешения** владельца проекта — отдельным согласованным PR.
3. Этот контракт описывает целевое поведение API; до реализации методов
   он не обещает доступность endpoint'ов в сборке.

## 9. Что остаётся за реализацией (не часть этого PR)

- Изолированная реализация хранилища (п. 8), отдельным PR после разрешения.
- HTTP endpoint и тесты (включая сценарий двух аккаунтов, п. 4).
- Rate limiting для чтения (образец — login).
- Staging: конфигурация и отдельная проверка резервного копирования
  и восстановления SQLite в изолированном контуре.
