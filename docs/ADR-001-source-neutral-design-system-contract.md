# ADR-001 — Source-neutral Design System Contract

Статус: **ACCEPTED**. Дата утверждения: **04.11.2026**. Решение владельца: **APPROVE**, утверждена редакция rev.2. История согласования: rev.1 — APPROVE WITH CHANGES; rev.2 — APPROVE. Дата исходного черновика: 04.11.2026.
Этап: **T1 завершён на уровне архитектурного проектирования**. Владелец решения: владелец ЗАРЯ. Утверждение ADR не означает реализации новых архитектурных слоёв.
База поставки: `9fb1399719b8f2e02a105844943e10b8e373c253` (merge PR #1).
Проверенный feature SHA: `1986326c713c87c2f360e0b66656d11518721284`; оба имеют дерево `767236ce7334037ae9d4b05dcb372e572250fb87`.

## 1. Контекст и проблема

В поставке работают Screen Schema v3, DS Contract 1.3.0, Registry из 15 записей, 57 токенов, runtime Validator, строгий Renderer, редакторский Canvas, миграции и восстановление JSON. Контракт разрешает ограниченный набор исходных компонентов и комбинаций. Schema validity не доказывает доступность реализации или визуальное соответствие. Исторические 14 определений / 171 вариант характеризуют матрицу образцов, а не полную функциональность.

Типы ComponentId и TokenName выводятся из WDeaf catalog; слоты, Figma IDs, варианты, токены и реализации зашиты в WDeaf-модули. Текущая архитектура отделяет часть проверок от React, но не отделяет контракт от конкретной дизайн-системы. MCP пока описан документом, не реализован.

Требования владельца:

- **Source-neutral:** сведения могут поступать из разрешённых design-first, code-first и hybrid источников.
- **Design-system-neutral:** общая модель не содержит обязательных имён Button, WDeaf, Figma node или конкретных токенов.
- Независимость формата контракта от React не означает наличие других платформенных Renderer. В T1 рассматривается существующий Web Builder.
- Универсальная совместимость — гипотеза для испытаний, не результат этого ADR.

В этом ADR не меняются исходный код, Screen Schema v3, Validator, Renderer, авторизация, Theme Editor, существующий ProjectRepository или архитектура работающего Workspace. Модель будущего Workspace ниже — только концептуальное уточнение. Не создаются адаптеры, transport, новые компоненты, интеграции Figma/Pixso/GitHub либо исполняемые схемы. Не запускаются T2–T7, Android/iOS и AI Builder.

## 2. Рассмотренные варианты

| Вариант | Преимущества | Недостатки | Решение |
| --- | --- | --- | --- |
| Обобщить текущий WDeaf Registry, добавив sourceType | Малый первоначальный diff | Сохраняет WDeaf union, зависимости слотов и смешение описания с исполнением | Не рекомендуется как целевая архитектура |
| Привести все библиотеки к одному набору универсальных компонентов/вариантов | Удобно для единого UI | Теряются исходные значения; появляются неподтверждённые эквивалентности и ложная совместимость | Отклонить |
| Отдельный полностью независимый stack на каждый источник | Меньше преобразований | Дублирование валидации, несовместимые правила и форматы документов | Отклонить как общий подход |
| Нейтральный описательный контракт + неизменяемые снимки + явные mappings и capabilities | Сохраняет происхождение, различия библиотек и границы исполнения | Требует версии контрактного формата, политики доказательств и разрешения контекста | **Рекомендуется концептуально** |

Не предлагается универсальный DSL для произвольных JS/CSS/HTML. Нейтральность достигается явными сущностями и ограничениями, а не возможностью выполнять любой код из источника.

## 3. Рекомендуемое разделение ответственности

| Слой | Вход → выход | Ответственность и границы |
| --- | --- | --- |
| Source Adapter | Разрешённый источник фиксированной ревизии → наблюдения с provenance | Чтение и нормализация формата; сохраняет исходные имена, неизвестное и конфликты. Не присваивает CR3, не регистрирует исполняемый код и не решает renderer support |
| DS Contract | Проверенные наблюдения + явно утверждённые правила → неизменяемое описание библиотеки | Компоненты, типы и допустимые значения props, точные комбинации, токены, слоты, ограничения родителей/детей и размещения. Не содержит React-компоненты или WDeaf-specific обязательные поля |
| Component Mapping Registry | Contract snapshot + source identities → закреплённые trusted implementation references | Явная связь определения/варианта с реализацией и преобразованием props. Проверяет версионный диапазон/точный digest. Никакого поиска по совпадающему displayName или динамического импорта из пользовательского JSON |
| Renderer Capability | Закреплённые mapping, implementation и evidence → матрица возможностей | Указывает поддержанные комбинации, состояния, операции, композиции, темы и ограничения среды. Не расширяет разрешённую структуру контракта |
| Validator | Контракт фиксированной версии + документ + policy → диагностика | Проверяет структуру и ограничения; выдаёт code/path/message. Не рисует UI, не извлекает источники, не сертифицирует визуальное соответствие по одному JSON |
| Screen Schema v3 | Существующий документ → тот же документ | Остаётся форматом WDeaf Web Builder. Не превращается автоматически в универсальный документ. Никакие новые поля libraryId/version в T1 не добавляются |

Поток данных и зависимости (концептуальная схема, не новая реализация):

```text
Разрешённые источники
        ↓
Source Adapter → наблюдения + provenance → утверждённый Library Snapshot / DS Contract
                                                    ↓                 ↓
Screen Schema v3 + закреплённый контекст ───────→ Validator       Mapping Registry
                                                    ↓                 ↓
                                           schemaValid        Renderer Capability
                                                    └───────┬─────────┘
                                                    readiness/evidence gate
                                                            ↓
                                                строгий render coordinator
                                                            ↓
                                                  trusted Web Renderer
```

DS Contract не зависит от Adapter или Renderer. Adapter зависит от формата наблюдений; Mapping зависит от версии контракта и реализации; capability зависит от mapping и evidence. Validator зависит от формата контракта и его фиксированного снимка. UI использует результаты и не определяет допустимость библиотечных свойств. Render coordinator в схеме — предлагаемая ответственность, не требование создать новый модуль в T1.

### 3.1. Project / Work / Document — будущая модель Workspace

Вводная владельца, зафиксированная концептуально:

| Сущность | Значение | Ответственность за источники и версии |
| --- | --- | --- |
| Project | Бренд, клиент или собственный продукт | Хранит подключённые источники и версии библиотек по умолчанию |
| Work | Конкретная именованная работа внутри Project | Объединяет редактируемые документы этой работы; не заменяет закрепление версий в Document |
| Document | Редактируемый документ внутри Work | Закрепляет конкретные неизменяемые снимки библиотек и runtime bindings, фактически использованные при работе |

Иерархия: `Project → Work → Document`. Настройки Project — значения по умолчанию для будущего выбора; они не являются динамическим binding существующего Document. При принятии библиотек в документе должны закрепляться точные снимки и runtime bindings. Изменение defaults Project не обновляет уже закреплённые версии в документах автоматически. Work не вводит скрытого приоритета версий над Document.

Document как концептуальная сущность шире payload Screen Schema v3: сведения о закреплении могут быть внешним контекстом, а сам JSON v3 остаётся неизменным. Формат и место хранения такого контекста пока не выбраны. Текущие ProjectRepository, Schema v3 и код Workspace не модифицируются; эта иерархия не объявляется уже реализованной.

## 4. Концептуальная модель контракта

Предлагаемые сущности (названия ниже — проект модели, не текущий API):

- **Library identity:** непрозрачный стабильный ID в namespace издателя; displayName отдельно. Имена разных библиотек не создают эквивалентности.
- **Definition identity:** ID определения внутри library; исходные имена и source locator сохраняются отдельно. Перенос или переименование не должны автоматически подменять identity.
- **Property:** исходное имя, тип, обязательность, подтверждённые значения/defaults, evidence. Отдельно: source property, редакторский контент, runtime state и события. Unknown не превращается в default.
- **Variant constraints:** точные подтверждённые комбинации либо явно описанное ограничение. Перечень значений каждого prop не разрешает автоматически их декартово произведение.
- **Token:** namespaced identity, исходное имя, тип, значение/alias, mode и evidence. Отсутствующий mode не додумывается. Alias требует разрешения внутри закреплённого набора; неизвестные ссылки и циклы запрещают соответствующее использование. Реализация aliases сейчас не заявляется.
- **Composition:** именованные слоты, типы детей, cardinality, ограничения родителей, root/internal role, согласование props. Отдельно различаются запрет и отсутствие доказательств. Разрешённый родитель сам по себе не создаёт реализованный слот.
- **Evidence:** источник и ревизия, locator, способ/дата получения, проверяющий, digest материала и область подтверждённого утверждения. Конфликтующие утверждения остаются видимыми.

Расширения контрактного формата требуют явной версии и обработки неизвестных полей. Нельзя выполнять функции, произвольные выражения, HTML, стили или URL из импортированного контракта. Закреплённая реализация выбирается из доверенного allowlist; подпись/хеш доказывает целостность, но не безопасность кода.

## 5. Три сценария источников

| Сценарий | Основание описания | Что нельзя заключать автоматически |
| --- | --- | --- |
| Design-first: Figma/Pixso | Подтверждённые metadata/variants/tokens/structure конкретной ревизии | Наличие executable реализации, интерактивности, CR2/CR3. Pixso здесь только будущий сценарий; его свойства и API не исследованы |
| Code-first: React/Storybook/разрешённый репозиторий | Закреплённый public API/types, реализация, stories и тесты с provenance | Что stories перечисляют весь контракт; что произвольные callbacks/children/style допускаются в документах Builder; что существуют Figma tokens |
| Hybrid | Два закреплённых источника + явно подтверждённое соответствие | Что одинаковые имена или Code Connect автоматически означают эквивалентность всех вариантов |

### Hybrid authority — полномочия источников и пользователя

- **Figma/Pixso:** утверждённый дизайн и визуальные свойства, когда библиотека design-first. Это не доказательство наличия исполняемой реализации.
- **React/Storybook:** исполняемая реализация и сведения о её поведении; наличие story само по себе не доказывает полноту проверок.
- **Code-first:** библиотека может не иметь Figma/Pixso. Отсутствие design-source не считается автоматически дефектом или основанием выдумывать его данные.
- **ЗАРЯ:** хранит правила, сопоставления и подтверждённые решения, включая происхождение и область полномочий каждого утверждения; не подменяет источник собственными неподтверждёнными свойствами.

В hybrid при расхождении нельзя молча выбирать «последний источник» или автоматически объединять списки props. Конфликт фиксируется на уровне конкретного утверждения; пользователь принимает явное решение, которое сохраняется вместе с проверяющим/автором решения, датой, областью, обоснованием и evidence. Разрешение конфликта не переписывает исходные сведения: новое решение относится к новой закреплённой ревизии.

**Подтверждение пользователя не снимает блокировку структурной ошибки и не заменяет отсутствующую Renderer Capability.** Даже после решения по источнику затронутая комбинация должна пройти структурную проверку, подтверждение capability и readiness gate; иначе строгий рендеринг остаётся заблокированным.

### Подтверждённый второй пример: Radix Primitives Checkbox

Официальная [документация Checkbox](https://www.radix-ui.com/primitives/docs/components/checkbox), прочитанная 04.11.2026, показывает версию 1.3.12 и части `Root`/`Indicator`. `checked` и `defaultChecked` имеют тип `boolean | 'indeterminate'`; `onCheckedChange` — функция; `disabled` и `required` — boolean. Это подтверждённые сведения API, а не заявленная поддержка в Builder. [Открытый исходник](https://github.com/radix-ui/primitives/blob/main/packages/react/checkbox/src/checkbox.tsx) доступен, но ссылка на main изменяема.

Архитектурный вывод: нейтральная модель должна сохранять union и различать состояние, события и композицию, не преобразуя их без доказательства в WDeaf `checked` + `indeterminate`. Callback не сериализуется как исполняемый код. Поддержка `asChild` не означает разрешение произвольных children в Builder. Для допуска нужна отдельная безопасная mapping-политика.

Radix не установлен, адаптер не написан, snapshot с package integrity/commit не создан, Renderer не проверен. Число поддерживаемых вариантов, токены, CR и совместимость с v3 — **не установлены**. Это ограниченный подтверждённый контрпример WDeaf-специфичным типам, не готовая вторая интеграция.

## 7. Component Readiness и гарантии Validator

| Уровень | Определение | Предлагаемое основание перехода |
| --- | --- | --- |
| CR0 | Импортирован | Есть наблюдения и provenance; данные могут быть неполными |
| CR1 | Описан контрактом | Подтверждены допустимые props/композиции и границы unknown; контракт проходит собственную проверку |
| CR2 | Реализован и прошёл базовые проверки | Есть закреплённый mapping/implementation и базовые функциональные проверки установленного subset |
| CR3 | Проверен в рамках установленного контракта | Есть доказательства по утверждённым состояниям, операциям, композициям и среде; известные ограничения явно включены в область проверки |

CR относится к **точной ревизии определения и заявленной области**, включая renderer/mapping/theme/environment. Один проверенный вариант не повышает всё семейство до CR3. Где нет evidence, уровень не присваивается предположением. Изменения реализации или зависимостей требуют нового evidence; старый immutable record сохраняется, не переписывается.

### CR3 review для дорожки A

Для дорожки A владелец может проводить **self-review**. В записи проверки сохраняются: тип проверки (self-review либо иной явно указанный тип), проверяющий, дата, область подтверждения и evidence. Область включает закреплённые снимок, runtime binding, состояния и операции, к которым относится вывод. Также явно сохраняются результат и открытые ограничения. Self-review не обозначается независимой экспертизой и не создаёт её гарантий.

Открытый риск React key и потери клавиатурного фокуса Checkbox/Chip должен учитываться при оценке затронутых операций. Пока удержание фокуса не подтверждено, эти операции нельзя объявлять проверенными по данному критерию или скрывать проблему общей меткой CR3. Допустима только явно ограниченная подтверждённая область; запрос за её пределами не проходит строгий gate. Self-review не обходит Validator и Renderer Capability и не присваивает текущим компонентам CR3 автоматически.

CR не является уровнем гарантии Validator. Предлагаются независимые результаты: целостность/разрешение контекста; структурная допустимость; renderer support; достаточность readiness/evidence. Не вводятся новые числовые уровни Validator, не согласованные владельцем. Успешная структура не доказывает поведение, доступность, pixel-perfect или безопасность реализации.

**Предлагаемый новый strict gate:** все использованные определения/вложенные и генерируемые части должны иметь CR3 для запрошенной области, документ должен быть структурно валиден, mapping разрешён, capability подтверждена, версии закреплены. Неполная область CR3 не даёт fallback на произвольный HTML/CSS или похожий компонент.

Это правило будущей архитектуры, а не описание текущего strict переключателя. Текущий strict WDeaf Renderer остаётся без изменений и не объявляется автоматически соответствующим новому CR3 gate. Дата и механизм перехода — отдельное решение после проверки evidence.

## 8. Неизменяемые снимки и закрепление версий

Предлагается три связанных, но разных идентичности:

1. **Library snapshot:** source observations + нормализованный контракт + provenance; immutable digest. Хранить bytes исходных артефактов и digest, правила canonicalization и версии нормализатора. Конкретный формат хеширования подлежит утверждению.
2. **Runtime binding:** точные mapping revision, implementation build/package integrity, renderer capability revision, зависимости/assets/fonts. Snapshot metadata сам по себе не закрепляет исполняемую реализацию.
3. **Evidence manifest:** тестируемая комбинация snapshot/runtime/environment, проверки, результаты, ограничения и правила признания CR. Не заменяется ссылкой «latest CI».

Версия формата контракта, upstream library version, source revision, mapping revision и Renderer version — разные поля. SemVer может объяснять совместимость, но не заменяет immutable digest. Для design-source без стабильной upstream revision сохраняется факт отсутствия версии и хеш полученного материала; нельзя выдумывать revision из даты.

Обновление создаёт новый снимок. Открытие, рендер или сохранение существующего Document не выбирают latest автоматически и не наследуют новые defaults Project вместо закреплённых версий. Недоступный, конфликтующий или отозванный binding блокирует использование с объяснением; исходный документ остаётся доступен для экспорта. Отзыв доверия не переписывает старый снимок.

## 9. Совместимость с неизменной Schema v3

У v3 нет library/snapshot reference. Добавить такие поля в текущий JSON означало бы изменить контракт; T1 это запрещает. Предлагается **внешний контекст разрешения**, а не скрытое расширение документа:

- Существующие WDeaf v3 с известным происхождением трактуются только в явно закреплённом legacy WDeaf profile. Кандидат baseline profile — поставка `9fb1399…`; ещё требуется проверить корпус более ранних v3, нельзя объявлять один снимок совместимым со всеми.
- Связь Document с профилем, фактически использованными снимками и runtime bindings хранится вне payload v3, например в отдельном binding manifest транспортного пакета. Его формат и место хранения не утверждены и не реализуются в T1; существующий ProjectRepository и архитектура работающего Workspace не изменяются.
- **Standalone legacy JSON без binding:** сначала сохраняется исходный документ без потери данных. Отсутствие binding не даёт права удалять неизвестные поля/элементы, применять defaults Project или подбирать библиотеку по совпадению имён компонентов, props либо токенов.
- Для **явно распознанного legacy WDeaf** пользователю разрешено выбрать соответствующий профиль. Распознавание должно опираться на подтверждённый контекст происхождения/экспорта, а не на совпадение имён. При необходимости пользователь явно указывает происхождение; его указание фиксируется как пользовательское утверждение, а не как автоматически доказанный provenance. Выбор не выполняется за пользователя и не означает успешной проверки документа.
- Если источник или подходящий профиль неоднозначен, предлагается **явное разрешение конфликта**: показать доступные подтверждённые сведения и различия, запросить осознанный выбор профиля/уточнение происхождения либо позволить отказаться. До разрешения и проверки соответствия строгий рендеринг заблокирован; исходник остаётся доступен для сохранения и экспорта.
- После явного выбора профиль и runtime binding закрепляются во внешнем контексте Document; затем независимо проверяются структура, Renderer Capability и readiness. Ошибка оставляет исходник неизменным и не запускает автоматическую миграцию. Конкретные признаки распознавания и полный UX разрешения конфликта ещё требуют проверки; здесь задана безопасная политика, а не реализованный импортёр.
- Новая библиотека, включая Radix, не становится доступной в текущем v3 union по факту публикации ADR. Поддержка второго источника в продуктивном документе требует отдельно согласованного bridge либо будущей версии формата. Это открытое решение, не автоматическая миграция.
- Документ и binding при будущем переносе должны передаваться совместно; потеря binding не разрешает fallback на latest. Байтовый хеш можно использовать для integrity, но он меняется после редактирования и не должен быть единственной устойчивой identity проекта.
- Обновление библиотеки — отдельная явная операция с отчётом несовместимостей, сохранением исходника и возможностью отказа. Не исправлять неизвестные props и не удалять элементы ради успешной проверки.

Нужны различимые причины отказа: неизвестное определение, отсутствующий snapshot/binding, недопустимая структура, неподдержанный Renderer subset, недостаточное readiness evidence. Названия будущих кодов ошибок пока не утверждаются.

Текущее поведение сохраняется: v3 round-trip сохраняет slots/tokenReferences/Select state; v1 radius >32 получает предупреждение; запрещённые legacy корни не удаляются; backup остаётся локальным. `toCanvasV2` допускает только представимый плоский subset без потери данных и возвращает V2_UNSUPPORTED для остального. Ни ADR, ни новый снимок не обещают универсальный downgrade.

## 11. Риски и известные ограничения

- Внешний контекст v3 может потеряться при одиночном экспорте JSON; требуется явная пакетная/legacy политика, без смены формата в T1.
- Переобобщение приводит к потере source semantics; особенно опасны callbacks, arbitrary children, state и variants.
- Частичная матрица и незакреплённые источники дают ложное ощущение полноты. Documentation main/tag без integrity не считается immutable runtime snapshot.
- CR3 без установленной области и evidence становится маркетинговой меткой; нельзя выводить его только из успешного CI.
- Hybrid конфликт разрешает пользователь в рамках явных полномочий источников; его подтверждение не отменяет структурные ошибки или отсутствие capability.
- WDeaf Validator проверяет ограниченную модель JSON, не произвольные JS getters/Proxy; transport/security policy за пределами T1.
- Существующие ограничения TagInput, TagGroup 1↔2, DropdownMenu, временного Input и локального storage сохраняются.
- Известный долг React key/фокус Checkbox и Chip остаётся; он должен входить в оценку readiness соответствующих операций, а не исчезать при переименовании уровней.
- Исторические разделы DESIGN.md и MCP_ARCHITECTURE.md содержат прежние версии. Для фактической базы использовать актуальные уточнения 1.3.0 и baseline SHA; эти документы здесь не переписываются.

## 12. Решения владельца и критерии готовности к T2

Владелец окончательно утвердил ADR-001 rev.2 решением **APPROVE от 04.11.2026**: source-neutral и design-system-neutral модель, разделение слоёв, неизменяемые снимки, отдельные mapping/capability/evidence, Project → Work → Document, CR0–CR3 и строгий режим для подтверждённой области CR3, безопасная политика Legacy v3, hybrid authority и обязательные проверки, Radix Checkbox как ограниченный пример, неизменная Screen Schema v3.

Утверждённые уточнения rev.2:

1. Модель Project / Work / Document и безопасное явное разрешение legacy binding.
2. Self-review дорожки A допустим с указанной областью и evidence, не является независимой экспертизой и учитывает открытый риск фокуса.
3. Hybrid authority не допускает обхода структурной валидации/Renderer Capability пользовательским решением.

Открытые решения, не подменяемые утверждением ADR:

- Формат и место внешнего binding, правила распознавания legacy provenance и будущий формат документов второго источника; без изменения v3 или ProjectRepository в T1.
- Точные критерии evidence CR3 и отдельное решение о переходе от текущего legacy strict к новому gate.
- Закреплённая revision/package и права использования второго источника до исполнения; Radix не считается реализованной интеграцией или автоматически утверждённой выборкой ADP-01.
- Передача и проверка полных протоколов и критериев Research Registry v0.3.3 для E3 Phase A и ADP-01 / E3 Phase B. Определения этапов уже переданы владельцем; повторное определение этих терминов не требуется.

Архитектурные основания T1 утверждены. Открытые вопросы сохранены для соответствующих следующих этапов; ответственные и scope дальнейших работ требуют отдельного согласования. **T2 пока не разрешён и не начат.** Определение подробной unsupported policy относится к T2 и здесь не считается выполненным.

Результат T1: **ADR-001 ACCEPTED; архитектурное проектирование завершено**. Новые архитектурные слои не объявляются реализованными. Утверждение документа не является разрешением начать T2–T7, создавать адаптеры или интеграции Figma/Pixso/GitHub, изменять Screen Schema v3, Renderer, Validator, ProjectRepository либо архитектуру работающего Builder.
