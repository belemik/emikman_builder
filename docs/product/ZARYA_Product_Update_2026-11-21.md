## 1. Продуктовое решение

ЗАРЯ должна поддерживать повторное использование компонентов и иконок между проектами без неявной массовой перезаписи. Предлагаются два самостоятельных пространства с явной связью через дизайн-систему:

- **Design System Studio → Component Board:** компоненты, варианты, параметры размеров и адаптивности, состояния, источник, версия, зависимости и область применения.
- **Assets → Icon Studio:** глобальные икон-паки и собственные SVG; для каждой дизайн-системы — выбранный, версионированный набор и конкретные настройки использования.

**Режим по умолчанию — Add Only.** Одобренное добавление создаёт новые записи и версию каталога. Существующие определения, иконки, snapshots, bindings и ревизии сохраняют зафиксированные версии. Внешнее изменение Figma-файла или npm-пакета само по себе не меняет страницы, снимки или код.

## 2. Component Board: требования

- Сетка компонентов с фильтрами: All / Figma / Code / Local, поиск, вариативность, статусы Supported / Mapping needed / Unsupported / Changed.
- Карточка компонента: ID, версия, DS snapshot, происхождение, доступные свойства/variants, preview, pages usage, зависимые токены, доступные действия.
- Inspector показывает ширину, высоту, max-width, padding, spacing, типографику, состояния и responsive rules только там, где конкретный контракт, mapping и Renderer Capability явно поддерживают поле. Режимы Supported / Mapping needed / Unsupported / Changed служат диагностикой интерфейса. Для строгого допуска требуется evidence в заявленной области по ADR-001 и T2/T3.
- Два уровня изменения. **Instance override** ограничен конкретной инстанцией одного Document и его базовой Revision. **Shared component change** проектирует новую версию определения или binding и показывает влияние на доступные пользователю зависимости и страницы. Массовая миграция между документами или проектами требует отдельной политики, разрешений и доказанной модели Apply.
- До изменения — Before/After с Desktop / Laptop / Tablet / Mobile / custom viewport, ScopeDiff и последствиями для responsive, доступности и существующих revision.
- Утверждение candidate, запись локальной ревизии и запись в GitHub требуют раздельных полномочий. Отмена, отказ, конфликт ревизий и неподдерживаемые свойства обрабатываются явно.

## 3. Figma Selective Sync: добавление без перезаписи

Планируемые режимы:

1. **Add Only (default).** Read-only scan предлагает только определения с новыми устойчивыми идентификаторами, отсутствующими в закреплённой версии Registry. Добавление в новый snapshot возможно после отдельного допуска. Предсуществующие DS/React-компоненты и их bindings сохраняются.
2. **Selective Update:** показать diff выбранных ранее сопоставленных компонентов, варианты, токены, зависимые страницы, влияние на доступность/макеты; подтверждение поэлементное.
3. **Replace.** Явное решение владельца, отдельный scope с полной картой ссылок и планом восстановления. При допущенном восстановлении создаётся новая ревизия. Совпадение имени не даёт права на замену.

Синхронизация требует авторизованного доступа к источнику, стабильных идентификаторов Figma (file key, node/component key/ID в зависимости от API и области источника), точной версии источника, если она доступна, и отпечатка наблюдённых данных. Идентификаторы, происхождение и fingerprint фиксируются отдельно от версии DS snapshot и mapping. Правила доступа к Registry, идемпотентности и хранения записи остаются предметом отдельного решения. **Одно лишь обновление URL в Figma не означает безопасную синхронизацию.** Переименование компонента не создаёт автоматически новый и не вызывает замену; удаление у источника не удаляет локальный объект. Дубликаты, несовместимые свойства и неподтверждённые tokens уходят в manual resolution.

**Граница:** Figma-нод не равен готовому React-компоненту. Сохраняется цепочка Source Adapter → DS Contract / snapshot → Component Mapping → Renderer Capability → Platform Adapter. Непроверенные элементы доступны для диагностики. Строгий preview и Apply закрыты до подтверждения необходимых возможностей. Подмена HTML/JS от LLM запрещена.

## 4. Icon Studio: библиотека, независимая от DS

Кандидаты в первый пилот — **Lucide** и **Tabler Icons**. **Phosphor**, **Material Symbols** и **Custom SVG** рассматриваются позднее. Доступность набора требует проверки состава, версии, происхождения и прав на использование. Опционально — каталог провайдеров по типу Iconify, но каждую коллекцию и условия использования проверять отдельно перед доступностью в продукте.

Модель:

- `IconPack`: `packId`, `source`, `packageVersion`, `licenseRef`, `rightsStatus`, `lastVerifiedAt`.
- `IconAsset`: `iconId`, `packId`, `sourceName`, `variant`, `svgFingerprint`, `metadata`, `renderCompatibility`.
- `DesignSystemIconBinding`: `designSystemId`, `snapshotVersion`, `semanticName`, `iconId`, `sizeToken`, `colorToken`, `strokeWeightToken`, `usageConstraints`.
- `ProjectIconUsage`: привязка к конкретным компонентам/страницам и revision для анализа воздействия.

Действия: поиск и preview, выбор и добавление иконок, новые пакеты, настройка в рамках DS tokens, импорт SVG, Add Only/Selective Update/Replace после approval. Сохранять точные версии и отпечатки. Общий каталог не предоставляет проектам общий доступ к приватным ресурсам. Каждое использование требует проверки прав на ассет и закреплённого DS binding. При несовпадении стиля новых иконок показывать предупреждение, а не заменять действующие иконки.

Для будущего Custom SVG нужен независимый допуск. До preview и импорта доверенный обработчик проверяет разрешённое подмножество, формат, размер и сложность. Скрипты, обработчики событий, внешние ссылки и опасные вложения запрещены. Preview использует локальные разрешённые данные. Для Iconify происхождение и права проверяются по каждой коллекции.

## 5. Архитектурные границы

- Не менять `Screen Schema v3`, WDeaf строгий Validator и Renderer ради компонентов страницы или икон-паков. Для веб-страниц — отдельный будущий **WebPage Contract** и адаптеры, только после Owner Decision.
- Сохранять `Project → Work → Document → Revision`. Контекст revision закрепляет snapshot, mapping, runtime и evidence вне payload Screen Schema v3. Candidate строится в разрешённом Scope. Validator проверяет полную копию, ScopeDiff независимо сравнивает её с закреплённой базой. Human Approval привязывается к точной ревизии и digest проверенного diff. CAS Apply с receipt и аудитом требует готовности Storage и отдельного разрешения записи. При неопределённом исходе использовать сверку receipt.
- Внешняя синхронизация начинается с read-only scan и proposal. Политика публикации новой версии Registry согласуется отдельно от Apply одного Document. Закреплённые документы остаются на своих версиях до явной операции миграции в разрешённом scope. Protected Core сохраняется.
- Не допускать произвольный AI-generated JS, скрипты импортированного репозитория, автоматический push/merge/deploy и раскрытие секретов.
- Production/P05 остаётся BLOCKED; все merges — отдельное разрешение владельца с актуальными проверками.

## 7. Приоритизация и условия запуска

- **Зависимости будущей интеграции.** Линия Editor ведётся через отдельные решения по Inspector v0.3 и Image Editing v0.4. Project Storage развивается параллельно с WebPage Contract Decision Gate. Сохраняемые WebPage revisions потребуют принятого WebPage Contract и допущенного Storage. Полная интеграция Repo-to-Canvas / Component Board зависит от этих условий и отдельного допуска. Синтетические пилоты могут обсуждаться раньше.
- **Отдельный дизайн/архитектурный прототип:** Component Board UX + `Add Only` на синтетических fixtures, без Figma API и без записи в production.
- **Следующий независимый пилот:** Icon Studio с локальным разрешённым набором и UI выбора, без автоматической смены DS и без network imports.
- **Позже.** Авторизованная Figma Selective Sync с тестами dedupe, changed/deleted/renamed, stable identity, collisions и восстановления требует отдельного Owner Decision.

## 8. Приёмка будущих пилотов

1. При 20 существующих и 3 новых определениях Add Only предлагает ровно 3. После допущенного добавления появляется новый snapshot. Raw bytes и digests ранее сохранённых определений, snapshots, bindings и ревизий страниц совпадают с исходными.
2. Изменение исходного существующего компонента → показывается Changed; не применяется до Selective Update и согласования.
3. Коллизия source IDs / renamed variant / unsupported prop → явное предупреждение, отсутствие тихого обновления.
4. Разрешённое изменение ширины одной инстанции сохраняет соседние инстанции и общую версию компонента. Proposal общей версии показывает затронутые usages до approval. Неизвестные зависимости блокируют миграцию.
5. Изменение икон-пака/версии не меняет иконки существующих ревизий; custom SVG с опасным содержимым отвергается.
6. Repo-to-Canvas не выполняет npm scripts импортированного кода без отдельной изоляции и разрешения; GitHub write требует scoped approval, а не только AI suggestion.
7. Stale revision, ScopeDiff mismatch, неизвестная обязательная проверка или провал Validator блокируют Apply. Автоматический merge в этот scope не входит.
