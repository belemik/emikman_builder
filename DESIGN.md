# WDeaf PRO 2.0 — Design System Contract 1.0.0

## Цель и граница доказательства

Контракт задаёт закрытую грамматику документа: разрешены только пять компонентов, их подтверждённые имена вариантов и ссылки на 20 проверенных токенов. В строгом Screen Schema нельзя описать произвольный HTML/JSX, CSS, style, className, children, обработчики, новые компоненты или новые токены. Неизвестные поля отклоняются, а не игнорируются.

Успех строгой проверки означает **соответствие документа разрешённой модели**, а не сертификацию результата рендера. Текущий Canvas использует приближённый CSS и произвольные редакторские overrides; его UI, авторизация и Theme Editor в этом этапе не изменяются. В Sprint 04 валидатор встроен в UI; строгий renderer проверяет также наличие реализации конкретного варианта. Чтобы доказать соответствие произвольного сгенерированного интерфейса, будущий renderer обязан принимать только строго проверенную схему и иметь отдельно проверенные реализации каждого компонента. Ни текстовый промпт, ни схема сами по себе не могут запретить внешнему генератору добавить CSS.

Контракт описывает существующий линейный список компонентов. Иерархия контейнеров, Grid/Stack, адаптивные layouts, маршруты и произвольные слоты не подтверждены и не разрешены. Оболочка Builder, профиль и форма входа находятся вне генерируемого экрана; Avatar и ButtonClose в оболочке не становятся автоматически доступными элементами Canvas.

## Токены и стили

Имена, типы, значения и узлы происхождения берутся только из `tokens.verified.seed.json`. `validateToken(name, {type, value})` может проверить точное совпадение значения и типа. `constructor`, `__proto__`, неизвестное имя, произвольный HEX вместо ссылки и новое значение существующего токена отклоняются.

`tokenReferences` — массив уникальных имён токенов, декларация зависимостей документа. Это **не** подтверждённая привязка токена к произвольному CSS-свойству и не API глобальной темы. Список не меняет рендер текущего Canvas. Пустой список разрешён: компонент использует свои внутренние подтверждённые значения. Значения токенов в документ не копируются и не переопределяются.

В strict `themeOverrides` обязан быть `{}`. Даже совпадающее с токеном число 4 или цвет #0055ff не доказывает разрешённую глобальную привязку. В частности `spacing/radius/radius-4` не является радиусом всех компонентов. В compatible сохраняются существующие primaryColor, radiusPx, fontFamily с предупреждением UNVERIFIED_STYLE. Нельзя молча удалять overrides или заменять их похожими токенами, чтобы добиться зелёной проверки. Пользователь может явно восстановить WDeaf в существующем Theme Editor.

Неподтверждены: полный набор variables/modes, глобальные радиусы, произвольные цвета и шрифты, адаптивность, точная геометрия всех состояний, Code Connect, готовые React Props API. Тема оболочки light/dark/system не является темой дизайн-системы документа.

## Screen Schema и версии

Типы: `src/design-system/schema.ts`. ComponentId, TokenName и discriminated union ScreenElement выводятся из сгенерированного каталога; enum-значения остаются строковыми литералами. ScreenSchema — строгий v3, ScreenDraft — совместимый v3 с редакторскими overrides. CanvasV1/CanvasV2 описывают прежние форматы. Пример со всеми пятью компонентами: `design-system/examples/screen.v3.json`.

Корневые поля v3: `schemaVersion: 3`, `platform: "web"`, `elements`, `themeOverrides`, `tokenReferences`. Элемент сохраняет прежние `id`, `component`, `variantProps`, `editorProps`. ID уникален, непустой, до 100 символов; максимум 500 элементов. JSON ограничен 2 МБ UTF-8 на входе parseScreen/migrateJSON/CLI. Runtime не выполняет ввод, не обращается к сети, DOM, React, localStorage или серверной авторизации.

`design-system/screen.schema.json` (draft 2020-12) описывает машинную структурную грамматику. Каноническое решение принимает TypeScript-валидатор: дополнительно проверяет уникальность ID, известную неподтверждённую комбинацию Checkbox и ограничения миграции. SchemaVersion относится к формату документа; CONTRACT_VERSION 1.0.0 — к политике проверки. Несовместимое расширение/ужесточение политики требует новой версии контракта и release notes; нельзя автоматически разрешать неизвестную будущую schemaVersion.

## API и миграция

- validateComponent(unknown): строгая проверка формы отдельного элемента и props по seed; межполевое семантическое правило Checkbox проверяет validateScreen.
- validateToken(unknown, expected?): существование токена и необязательная сверка типа/значения.
- validateScreen(unknown): strict по умолчанию. `{mode: "compatible"}` разрешает только исторические редакторские расширения с предупреждениями, не неизвестные компоненты/props/токены.
- parseScreen(raw): ограничение размера, JSON-разбор и проверка v3 без неявной миграции.
- migrateScreen / migrateJSON: v1/v2 → ScreenDraft v3, v3 проверяется без повторной трансформации. Это не выдача сертификата strict. После миграции обязательно вызвать validateScreen для строгой проверки.
- toCanvasV2: проверенный v3 → v2 для существующего импортера. tokenReferences опускается с предупреждением TOKEN_MANIFEST_OMITTED; исходный v3 нужно сохранить отдельно.

v2 → v3 сохраняет ID, порядок, props и все overrides; добавляет пустой tokenReferences. v1 переименовывает theme.radius в themeOverrides.radiusPx и сохраняет цвет/шрифт. Радиус 33–48 ограничивается 32 **так же, как в существующем импортере**, с RADIUS_CLAMPED; исходный объект не меняется, исходный файл CLI не перезаписывает. Это единственная документированная потеря при миграции v1; оригинал нужен для полного восстановления. Неизвестные поля/версии и некорректный исходный JSON отклоняются до миграции.

Существующий UI продолжает читать/писать v1/v2. В Sprint 04 UI принимает v3 через toCanvasV2 с предупреждением об отсутствии token manifest в хранилище v2. Новый код не меняет localStorage или исходные проекты. Результат успешной проверки — независимая копия документа; последующее изменение входа не меняет результат.

## CLI, ошибки и доказательства

```sh
npm run ds:validate
npm run ds:validate -- path/to/project.json
npm run ds:validate -- --compatible path/to/legacy.json
npm run ds:generate
```

Без аргументов проверяются синхронизация seed → артефакты, TypeScript (включая отрицательные type assertions) и эталонный экран. CLI мигрирует v1/v2 в памяти, затем применяет strict, если не указан --compatible. Exit 0 — проверка выбранного режима прошла; 1 — документ/чтение не прошли; 2 — неверные аргументы. Вывод включает режим, версию контракта, errors и warnings; каждая ошибка имеет code/path/message. compatible никогда не маркируется как сертификат DS.

Тесты покрывают все enum-значения и boolean каждого компонента, неизвестные компоненты и style/props, неверные токены/значения/типы, смешанное состояние Checkbox, версии, миграцию и обратный импорт, отдельность результата, дубли ID, ограничения, CLI exit codes и compile-time ошибки. Будущий рендерер должен иметь отдельные проверки DOM/CSS, доступности, интерактивных состояний и визуальные сравнения с Figma. До этого доказана только закрытость модели документа.

Архитектура будущего MCP: `docs/MCP_ARCHITECTURE.md`; сервер и transport пока не реализованы.
